# Individual operator access

Implementation and acceptance are tracked in the [local issue](issues/operator-security.md).

* Keep the existing 12–128 character and individually salted PBKDF2-SHA256 policy. Require upper and lower case, digit, punctuation, exclusion of the account name ignoring case, and a different password on change.
* Each named account has one role. System administrators manage tenant configuration, integration clients and quota operations. Security administrators manage operator status and revoke operator sessions. Auditors read sign-in outcomes and management operations, including identity changes. Only the trusted host CLI provisions identities or recovers passwords. The deployment readiness check requires an active individual with a current password for each role. A vacancy leaves other individual accounts operational. Deployment creates missing role-named accounts and delivers an independent temporary password to each designated holder through a private host file. Additional personal accounts retain the existing enrollment flow. Bootstrap passwords can only be used to set the first personal password. The 90-day lifetime starts at that rotation. Readiness distinguishes pending first use from uncovered roles.
* Credential age starts on the actual password change. Login and every session lookup enforce a 90-day deadline. Allow current-password rotation at login, including after expiry, and revoke previous sessions. Remove the shared deployment bearer. Scripts can present an individual short-lived session as bearer.
* Existing accounts must be explicitly enrolled with a role and a different password. Unknown ages and roles grant no access. Retire all pre-migration sessions. SQLite and MySQL upgrades must preserve business data.
* Verify role isolation, legacy bearer rejection, migration, password boundaries, cross-session expiry and browser operation. Production changes and remote publication are outside scope.
